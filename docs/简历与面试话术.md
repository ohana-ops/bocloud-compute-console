## 二、项目介绍话术（STAR 结构，约 2 分钟）

**S（背景）：**
> 我想做一个贴近云原生 / 算力运营业务场景的后台系统，但不想从零搭一套用户、权限、菜单、日志这些基础能力。所以我选了开源的若依微服务框架作为底座，它自带完整的 RBAC 权限体系和微服务基础设施，我在它的基础上二次开发算力资源管理这个业务方向。

**T（任务）：**
> 核心业务闭环是「资源申请 → 管理员审批 → 资源分配 → 使用统计」，我需要新增一个独立的业务微服务，完成资源、申请单、分配记录三张业务表，以及对应的后端接口和前端页面。

**A（行动）：**
> 我新增了 `ruoyi-bocompute` 微服务模块（端口 9400），设计了 `biz_resource`、`biz_resource_apply`、`biz_resource_alloc` 三张表，开发了 4 个 Controller、3 套 Mapper + Service。审批通过这个操作，我把「占用资源 + 更新申请单 + 写入分配记录」放在同一个 `@Transactional` 事务里。资源扣减我没有用「先查再改」的方式，而是把 `available_count >= n` 的条件直接写进 update 的 where 里，通过返回影响行数判断是否扣减成功，从而避免并发超卖。前端 5 个页面通过若依的动态菜单自动加载，不需要改路由代码。

**R（结果）：**
> 最终跑通了从资源纳管到申请、审批、分配、统计的完整闭环，编译通过、前端页面可正常展示，多角色权限（普通用户申请 / 管理员审批）可以正常隔离。

## 四、面试高频问题与参考答案

### 1. 你为什么不直接写 CRUD，而是选了若依？

> 若依提供了完整的 RBAC 权限、动态菜单、操作日志、代码生成、多数据源等基础能力，这些是企业后台系统的通用底座。我的目标是聚焦「算力资源管理」这个业务域，复用底座能让我把精力放在业务逻辑上，也更贴近真实企业"基于已有框架二次开发"的场景。

### 2. 审批通过后怎么保证资源数量不超卖？

> 我没有用「先查询剩余数量 → 判断 → 再更新」这种方案，因为它在并发下会出现「读到的都是旧值，两个请求都通过」导致超卖。我把数量校验下沉到了 update 语句里：

```sql
update biz_resource
set used_count = used_count + #{count},
    available_count = available_count - #{count}
where resource_id = #{resourceId}
  and available_count >= #{count}
```

> 如果 `available_count` 不够，这个 update 影响行数为 0，我就抛出业务异常回滚整个事务。数据库行锁保证了并发下同一行资源的更新是串行的，天然安全。

### 3. 审批通过涉及多张表，怎么保证一致性？

> 原来的顺序是「占用资源 → 更新申请单 → 写分配记录」，三步放在同一个 `@Transactional(rollbackFor = Exception.class)` 方法里。
> 加了调度层之后改成六步：先插入分配单拿到 `allocId` → 调度器选卡并锁定设备 → 写入分配单-设备绑定 → 回写卡号到分配单 → 按设备汇总回写库存 → 最后才把申请单改为已通过。
> 关键点是「先插分配单再锁设备」，因为设备必须绑定到一个已存在的分配单；同时申请单状态放在最后一步改，这样调度失败时单据仍然是待审批，不会出现「单子通过了但没拿到卡」的中间态。

### 3.1 你说的调度是什么，真的连了 GPU 集群吗？

> 要坦白讲清楚：卡是模拟的，不是机房里的 PCIe 设备。我自研了一层模拟设备池调度——设备是 MySQL 里的一行记录（卡号、节点、槽位、状态），审批通过后由调度器从设备池里按同节点优先（binpack）选出具体设备、把状态置为已分配并绑定分配单，再把卡号回写到分配记录上，用户在页面上能看到自己拿到的是哪几张卡。没卡就整单回滚。
> 真实集群调度（K8s Device Plugin）我做成了可替换的接口 `ComputeScheduler`，现在跑的是设备池实现 `DevicePoolScheduler`，`K8sComputeScheduler` 是预留空壳，通过配置项 `bocompute.scheduler.type` 切换。

### 4. 前端页面怎么和权限菜单对接的？

> 若依的前端是「菜单驱动路由」。我在 `sys_menu` 表里插入了业务菜单，`component` 字段写的是 `bocompute/resource/index` 这种路径，前端 `permission.js` 里通过 `loadView('@/views/' + view)` 动态 import 对应的 vue 文件。所以只要菜单配对了、vue 文件建对了，页面就会自动出现，不需要改路由配置文件。按钮级别的 `@RequiresPermissions` 对应菜单里的按钮权限标识。

### 5. 你新增的模块怎么被注册中心和网关发现的？

> 我在 Nacos 配置里新增了 `ruoyi-bocompute-dev.yml`（数据源、Redis、端口等配置），启动类用了若依封装的 `@EnableCustomConfig` 和 `@EnableRyFeignClients` 自动注册到 Nacos。同时在网关的路由配置里追加了 `/bocompute/**` 到 `ruoyi-bocompute` 服务的转发规则，否则前端请求会 404。

### 6. 资源释放是怎么做的？

> 分配记录有 `release_time` 字段。手动释放时：调度器先把本次分配绑定的设备状态改回空闲并清空绑定信息，绑定明细置为已释放，再按设备汇总回写库存，最后把分配状态改为「已释放」并记录释放时间，整个过程在事务里。
> 另外还有一个 `AllocExpireTask` 定时任务，每分钟扫描「使用中且结束时间已过」的分配单，逐条调同一个 `releaseAlloc` 自动还卡，单条失败只记日志不影响其他，开关是 `bocompute.scheduler.auto-release-enabled`。

### 7. 如果让你扩展，你会加什么？

> 第一是把 `K8sComputeScheduler` 从空壳实现成真实调度——调用 K8s API 按 `nvidia.com/gpu` 这类资源申请 Pod，把调度到的 nodeName 和 GPU UUID 回填到设备表；第二是加计量计费，按 GPU 卡时计费生成账单；第三是加审批流引擎（Flowable）支持多级审批和会签；第四是监控告警，采集资源使用率与设备故障率并阈值告警。
